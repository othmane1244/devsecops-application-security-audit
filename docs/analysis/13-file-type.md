# Analyse de `file-type`

## Périmètre et détections

Le rapport Trivy initial inventorie sept installations sous `juice-shop/node_modules` : `file-type@16.5.4` à la racine, `11.1.0` sous `download`, `3.9.0` sous `decompress-unzip`, `4.4.0` sous `archive-type`, deux copies `5.2.0` sous `decompress-tar` et `decompress-targz`, et `6.2.0` sous `decompress-tarbz2`. Le rapport signale une détection `CVE-2026-31808`, MEDIUM, sur la copie racine `16.5.4` (`juice-shop/node_modules/file-type/package.json`). Le champ `Status: fixed` et `FixedVersion: 21.3.1` indiquent qu’une version correctrice est publiée; ils ne signifient pas que l’installation est déjà corrigée : `InstalledVersion` reste `16.5.4`, dans la plage affectée. Le rapport HIGH/CRITICAL n’a aucune détection `file-type`.

La vérification Docker en lecture seule ci-dessous confirme maintenant, pour le chemin de profil, l’appel dans le JavaScript compilé présent dans le conteneur arrêté dont les couches correspondent au rapport. Les sources publiées des consommateurs `download` et `decompress-*` continuent d’indiquer les consommateurs directs des copies imbriquées; leur utilisation applicative n’est pas déduite du seul arbre de dépendances.

## Avis officiel et mécanisme

L’avis mainteneur GHSA-5v7r-6r5c-r473 indique comme versions affectées `>=13.0.0, <21.3.1` et comme version corrigée `21.3.1`. Un fichier ASF (conteneurs WMV/WMA) forgé avec une sous-en-tête de taille nulle fait calculer une charge utile `-24`; `tokenizer.ignore(payload)` recule alors la position et la boucle relit la même sous-en-tête sans fin. L’avis indique qu’un fichier de 55 octets suffit à bloquer la boucle événementielle lorsque l’application demande à `file-type` d’identifier une entrée non fiable ou contrôlée par un attaquant [1].

La source publiée exacte de `file-type@16.5.4` contient bien le chemin ASF concerné : détection de la signature ASF, calcul `header.size - 24`, boucle de lecture et appel à `tokenizer.ignore(payload)` [3, extrait 1]. Cette version est dans la plage affectée; les copies `11.1.0`, `3.9.0`, `4.4.0`, `5.2.0` et `6.2.0` sont en dessous du seuil minimal de l’avis et ne sont pas concernées par ce GHSA.

Le correctif publié ajoute un contrôle de progression : il mémorise la position avant lecture et quitte la boucle si la position n’a pas avancé après `ignore` [4]. La source v16.5.4 commente que l’en-tête doit être recherché dans le premier KiB, mais la condition de boucle affichée ne borne pas explicitement la position à 1 KiB; ce commentaire ne neutralise donc pas le cas de recul décrit par l’avis.

## Provenance des octets et contrôles applicatifs

Dans les sources publiées du tag v20.3.0, `server.ts` configure `multer.memoryStorage()` avec une limite `fileSize: 200000` octets [2]. Le même fichier monte séparément `/file-upload`, `/profile/image/file` et `/profile/image/url`. La route URL récupère son contenu avec `fetch(url)` et l’écrit directement dans les fichiers d’images; le code source publié consulté ne passe pas ces octets à `file-type` [5]. La validation du formulaire `/file-upload` inspecte l’extension du nom de fichier plutôt que sa signature [6].

Le flux pertinent est confirmé : le gestionnaire compilé de `POST /profile/image/file` appelle `fileType.fromBuffer(file.buffer)`. Multer conserve l’upload en mémoire avec une limite de 200 000 octets, supérieure aux 55 octets décrits par l’avis. La route n’utilise pas les middlewares de challenge `checkUploadSize` et `checkFileType` montés sur `/file-upload`; elle applique son propre contrôle MIME dans le gestionnaire. L’authentification de l’utilisateur est vérifiée après l’analyse du buffer, donc elle ne protège pas ce parsing. Cela confirme un chemin de code disponible, pas une requête reçue ni une exploitation.

Le handler est asynchrone et attend `fromBuffer`. La source publiée complète de `asyncHandler` au tag exact transmet les rejets à `next`, mais le JavaScript compilé livré dans l’image s’arrête physiquement avant son corps : cette propagation est documentée comme comportement de la source, pas confirmée pour le build image. |
| Exploitation / blocage en production | Non démontrés; aucune requête ou exploitation n’a été exécutée. |

## Conclusion

Le rapport initial et le manifeste de l’image confirment `file-type@16.5.4`; le code compilé du gestionnaire appelle son parseur sur le buffer multipart du profil. Les contrôles MIME viennent après ce parsing; l’authentification vérifiée dans le handler vient également après. La taille maximale Multer de 200 000 octets n’exclut pas le fichier de 55 octets décrit par l’avis. **Le chemin d’analyse est présent dans l’artefact inspecté**, mais aucune requête n’a été effectuée et le conteneur est arrêté : l’exposition en cours ou une exploitation ne sont pas démontrées.

La source publiée complète de Juice Shop v20.3.0 décrit `asyncHandler` comme `Promise.resolve(fn(req, res, next)).catch(next)` [8]. Comme l’argument `fn(...)` est évalué avant l’appel à `Promise.resolve`, une exception synchrone lancée par un handler non `async` ne serait pas attrapée par ce `.catch`. Ici, le handler de profil compilé est une fonction `async` et attend `file-type.fromBuffer`; une exception interne ou un rejet du parser devient donc un rejet de la promesse du handler, que le wrapper publié transmettrait à Express. En revanche, le fichier effectivement extrait de l’image, `build/lib/utils.js`, mesure 9 457 octets (SHA-256 `038673f19775e10098927211afd6b1393fe5205b60c2d91ea214d32f228dfee3`, 236 lignes) et s’arrête au milieu du commentaire de `asyncHandler`, avant toute affectation de son implémentation. L’export est initialisé à `undefined` au début du fichier. Ce n’est pas une troncature de l’affichage : le flux tar complet a été lu et haché. Le code de montage compilé appelle `utils.asyncHandler(...)`; si cette séquence est exécutée avec ce fichier inchangé, l’appel devrait échouer synchroniquement au montage. Cela peut être compatible avec l’état arrêté observé, mais la cause de la sortie 255 et le comportement runtime n’ont pas été établis. La fonction compilée de l’image diffère de la source publiée attendue.

Cette distinction ne neutralise pas le déni de service décrit par l’avis. `fromBuffer` est une fonction `async`; le chemin ASF contient des `await` sur les lectures et sur `tokenizer.ignore`. Un parsing qui rejette sa promesse peut être transmis par le wrapper publié. Le cas CVE décrit autre chose : une boucle qui recule la position et relit indéfiniment le même en-tête. Un wrapper `.catch(next)` ne borne, n’annule ni ne récupère un parseur qui ne termine pas. Le code et l’avis qualifient ce cas de blocage de la boucle événementielle; aucune exécution n’a été faite pour caractériser indépendamment son ordonnancement dans cette image.

## Limites de vérification

### Complément — vérification Docker en lecture seule (28 octobre 2026)

- **D-01 — moteur, image et identifiants.** Le client Docker 29.1.2 et le moteur Linux sont accessibles dans le contexte `desktop-linux`. Le tag local `bkimminich/juice-shop:v20.3.0` existe. Les deux valeurs comparées sont de même nature : `Metadata.ImageID` du rapport Trivy et `Id` de `docker image inspect`, tous deux des identifiants SHA-256 de configuration d’image; ils diffèrent (`40606c…` contre `cea5a4…`). Les deux configurations ont le même `created`, OS/architecture, commande, entrypoint, environnement, utilisateur, répertoire de travail, port exposé et labels, sauf `org.opencontainers.image.created` : le JSON du rapport contient U+201D autour de l’horodatage, tandis que l’image locale contient `?` (U+003F). Ce seul champ de label divergent explique la différence de configuration observée; les 24 `RootFS.Layers` / `DiffIDs` sont identiques, donc le contenu des couches correspond. Cela établit la concordance des couches, non l’identité des configurations ni une provenance historique certaine du scan.
- **D-02 — conteneur existant, pas état runtime.** `juice-shop-audit` référence l’ID local, n’a aucun montage et est à l’état `exited` (code 255). Aucun conteneur Juice Shop n’est en cours d’exécution. Son environnement stocké ne contient que les noms `PATH` et `SSL_CERT_FILE`; aucun réglage Juice Shop de profil/challenge, port ou chemin de base n’est défini. Le conteneur a des changements de fichiers sous `data`, `frontend`, `ftp`, `i18n` et `logs`; `docker diff` n’en signale pas sous `build`, `config`, `routes` ou `server.ts`. Ces constats ne décrivent pas une exécution active.
- **D-03 — déclaration de route et parser compilés.** Dans le système de fichiers inchangé à ces chemins, `build/server.js:345` contient l’expression d’enregistrement de `POST /profile/image/file` avec `uploadToMemory.single('file')`, `ensureFileIsPassed`, la métrique puis `utils.asyncHandler(profileImageFileUpload())`. `build/server.js:690` configure Multer en mémoire, avec `fileSize: 200000`. `build/routes/profileImageFileUpload.js:49-90` définit le handler asynchrone qui vérifie le buffer, attend `file_type_1.default.fromBuffer(buffer)`, rejette les types non `image`, vérifie ensuite le cookie utilisateur, écrit l’image et met à jour le modèle. Le manifeste `node_modules/file-type/package.json` indique `16.5.4`, concordant avec le finding. L’expression de montage existe dans les fichiers; l’export compilé d’`asyncHandler` étant laissé à `undefined`, un enregistrement effectif avec ces fichiers exacts n’est pas démontré et devrait lever une exception synchrone.
- **D-04 — contrôles et erreurs.** Le middleware `ensureFileIsPassed` (`build/routes/fileUpload.js`) retourne 400 si aucun fichier n’est reçu. Dans le handler, un buffer absent ou un résultat `undefined` donne 500; un résultat `null` ou un MIME qui ne commence pas par `image` donne 415. Une absence d’utilisateur transmet une erreur à Express. L’échec d’écriture est seulement journalisé; l’échec de mise à jour utilisateur passe à `next(error)`. Le handler compilé est `async` et attend `fromBuffer`. La source publiée complète indique un `.catch(next)` pour `asyncHandler`; le fichier compilé de l’image initialise son export à `undefined` et s’arrête avant le corps. Le comportement de forwarding est établi pour le code publié seulement, et reste absent du JavaScript livré. Si la séquence de montage s’exécute inchangée, une erreur synchrone est attendue; aucune exécution n’a vérifié ce résultat ni la cause de l’état de sortie 255.
- **D-05 — fichiers de configuration de l’image.** `config/default.yml:89` fixe le défaut image `challenges.safetyMode: auto`. Les profils présents `ctf.yml:12` et `defcon33.yml:48` contiennent `disabled`; `unsafe.yml:2` contient littéralement `disable` (forme différente des valeurs `enabled`, `disabled`, `auto` documentées dans le commentaire de `default.yml`). L’effet de cette valeur ne doit pas être supposé. Les chemins de configuration sont inchangés dans le conteneur arrêté et aucun environnement applicatif n’est défini; cela n’identifie pas le profil qui aurait été chargé lors d’une exécution passée.

Les contenus ci-dessus ont été lus via le système de fichiers du conteneur arrêté; l’identité des couches avec le rapport, l’absence de montage et l’absence de changements dans les chemins cités les relient à l’image analysée. Ils prouvent le contenu statique de l’artefact, **pas la configuration ou le comportement runtime**. Aucun conteneur n’a été démarré; aucun scan, appel applicatif ou test d’exploitation n’a été lancé.
