# 17 — messageformat

## Résumé

Le rapport Trivy initial inventorie une seule installation `messageformat@2.3.0` et l’associe à `CVE-2025-57349` (LOW; état Trivy `fixed`, correctif annoncé `3.0.0-beta.0`). L’avis officiel définit pourtant les versions affectées comme strictement antérieures à `2.3.0`; la version inventoriée est donc à la borne exclue. L’écart entre la borne officielle et la version corrective affichée par Trivy est conservé comme tel.

Le consommateur publié identifié est `i18n@0.11.1`. Son API `__mf()` appelle bien `MessageFormat.compile()`, puis exécute la fonction compilée avec les valeurs nommées. Dans `messageformat@2.3.0`, la compilation accepte aussi des objets imbriqués et parcourt leurs clés. Toutefois, aucun appel applicatif à `__mf()` n’a été établi dans les sources Juice Shop consultées; le code publié d’i18n seul ne prouve donc pas que ce chemin soit atteint. L’exploitation n’est pas démontrée.

Le titre est « messageformat has a prototype pollution vulnerability ». |

Il inventorie aussi `make-plural@4.3.0` sous `messageformat/node_modules`. |

## Avis et code de la version exacte

| Preuve | Constat |
|---|---|
| M-05 | L’avis officiel [GHSA-xfqm-j7pc-xrfc / CVE-2025-57349](https://github.com/advisories/GHSA-xfqm-j7pc-xrfc) donne la plage affectée `< 2.3.0` et affiche `3.0.0-beta.0` comme version corrigée. Il décrit une pollution de prototype via des clés spéciales, dont `__proto__`, dans des messages imbriqués. Selon cette plage, `2.3.0` n’est pas affectée. |
| M-06 | L’issue amont [#452](https://github.com/messageformat/messageformat/issues/452) reprend la borne « prior to 2.3.0 », mais sa section de détails cite aussi `messageformat@2.3.0`; l’issue a été fermée « not planned ». Cette incohérence ne permet pas d’élargir la plage officielle à `2.3.0`. Trivy marque l’occurrence « fixed » tout en affichant `3.0.0-beta.0`; l’étiquette Trivy n’est pas une preuve qu’une version installée `2.3.0` soit dans la plage affectée.
| M-07 | Le code publié au commit de release [`cd47ed7`](https://github.com/messageformat/messageformat/tree/cd47ed7db2b7a4f5e21df4cd6284ae3f7dad05a1), identifié comme `messageformat@2.3.0`, décrit `compile(messages)` comme acceptant une chaîne ou un objet hiérarchique. Dans [`messageformat.js`](https://github.com/messageformat/messageformat/blob/cd47ed7db2b7a4f5e21df4cd6284ae3f7dad05a1/packages/messageformat/src/messageformat.js#L15-L22), `_stringify` parcourt les propriétés de l’objet et `compile` appelle le compilateur avec `messages`; pour un objet, il génère ensuite un objet de fonctions. Le [compilateur](https://github.com/messageformat/messageformat/blob/cd47ed7db2b7a4f5e21df4cd6284ae3f7dad05a1/packages/messageformat/src/compiler.js#L2-L4) descend récursivement dans les objets et construit `result[key]`. Ce parcours rend les clés du message pertinentes au mécanisme décrit par l’avis. La présence de ce code publié ne démontre ni une exploitation de la version 2.3.0 ni l’atteignabilité depuis l’application.

## Appels et provenance des valeurs

| Preuve | Constat |
|---|---|
| M-08 | Dans la source taggée [`i18n@0.11.1/i18n.js`](https://github.com/mashpie/i18n-node/blob/0.11.1/i18n.js#L253-L295), `__mf(phrase)` sélectionne la locale de l’objet d’appel ou celle d’un argument `{ phrase, locale }`, obtient `msg = translate(targetLocale, msg)`, crée ou réutilise `new Messageformat(targetLocale)`, désactive la validation des clés plurielles et appelle `mf.compile(msg)` uniquement si la fonction n’est pas déjà en cache. Il rend ensuite avec `f(namedValues)`, puis applique les substitutions complémentaires. Le cache mentionné concerne les compilations par locale/message; il ne supprime pas le premier appel à `compile` pour un message nouveau. |
| M-09 | L’entrée `phrase` fournie à `__mf` est d’abord une clé de consultation du catalogue, ou un objet contenant la clé et une locale. Le texte effectivement compilé vient de `translate()` et donc du catalogue de la locale; les données nommées sont un argument distinct utilisé au rendu, après compilation. Le code `__mf` ne transforme pas les données de rendu en arbre de définitions de messages. Si la valeur du catalogue est elle-même un objet imbriqué, le code fourni ne la réduit pas à une chaîne avant `compile`; cette forme peut donc atteindre le compilateur objet. La présence de clés spéciales dans les catalogues effectivement déployés n’est pas établie ici. |
| M-10 | Le manifeste Juice Shop [v20.3.0](https://github.com/juice-shop/juice-shop/blob/v20.3.0/package.json#L126) déclare i18n comme dépendance. [`server.ts`](https://github.com/juice-shop/juice-shop/blob/v20.3.0/server.ts#L300-L308) configure la liste des locales depuis `data/static/locales.json`, un répertoire `i18n`, la locale par défaut `en` et le cookie `language`, puis monte `i18n.init`. Dans i18n 0.11.1, les valeurs de cookie / en-tête servent au choix de la locale, tandis que `setLocale` retient une locale existante ou retombe sur la valeur par défaut (lignes 645–680, 406–412). L’utilisateur peut donc influencer la sélection proposée, mais pas ajouter par cette seule valeur une locale arbitraire aux catalogues configurés. |
| M-11 | Un appel applicatif ordinaire `res.__()` est visible, par exemple dans [`routes/login.ts`](https://github.com/juice-shop/juice-shop/blob/v20.3.0/routes/login.ts#L43-L47). Aucun appel `__mf()` n’a été observé dans les sources applicatives consultées. En conséquence, l’existence de l’API et du consommateur `i18n` ne vaut pas preuve d’un appel applicatif de compilation/rendu. Les textes des catalogues, leur contenu exact dans l’image, leur éventuelle modification de déploiement et l’absence d’autres appels sur l’ensemble des fichiers effectivement livrés dans l’image ne sont pas vérifiables à partir des rapports JSON. |

### Contrôle des entrées et prérequis

- **Texte / structure du message :** l’avis requiert des définitions imbriquées avec une clé spéciale. Dans le chemin i18n, le contenu compilé provient du catalogue local choisi, pas des seules variables fournies pour le rendu. La présence d’une définition imbriquée contenant la clé concernée dans les catalogues de l’image reste inconnue.
- **Locale :** la configuration publiée limite les locales à une liste issue du fichier statique `data/static/locales.json`, avec `en` comme défaut. Le cookie `language` est contrôlable par le client, mais i18n rabat les locales absentes du catalogue sur la locale par défaut. Le contenu réel du fichier image n’a pas été extrait ici.
- **Options :** Juice Shop configure `i18n` (dont `directory`, `cookie`, `defaultLocale`, `autoReload`), mais aucun paramètre d’options direct de `MessageFormat` n’est fourni par cet appel; i18n construit `Messageformat(targetLocale)` sans objet d’options, puis appelle `disablePluralKeyChecks()`. Les options par défaut de MessageFormat sont donc celles du code publié.
- **Données injectées :** `namedValues` et les arguments de format sont distincts du message compilé et atteignent le rendu/substitution après compilation. Aucun appel `__mf` dans une route transmettant des données utilisateur n’est établi.
- **Prérequis à l’exploitation :** il faudrait qu’un chemin applicatif appelle effectivement `__mf` avec une traduction objet comprenant la structure/clés visées, et que le mécanisme soit exploitable avec la version résolue. Ces conditions ne sont pas réunies par les preuves disponibles; elles ne sont pas déclarées impossibles pour tout code/configuration ajouté au déploiement.

## Conclusion et limites

**Détection Trivy présente; mécanisme exploitable dans l’installation signalée non confirmé.** La version rapportée `2.3.0` est exclue de la plage officielle `<2.3.0`, malgré la version corrective `3.0.0-beta.0` annoncée par GHSA et Trivy. Le source publié de 2.3.0 conserve un parcours récursif d’objets piloté par leurs clés, tandis que le consommateur `i18n@0.11.1` peut compiler une valeur de catalogue objet via `__mf`. Cependant, aucun appel applicatif `__mf`, aucune définition spéciale pertinente dans les catalogues et aucune exploitation ne sont établis. Les rapports Trivy prouvent la présence et le chemin de l’installation dans l’image scannée; ils ne fournissent pas les fichiers JavaScript ou catalogues extraits de l’image. Les sources GitHub citées sont des sources publiées taggées/commit précis, pas une vérification indépendante du contenu réellement embarqué.
