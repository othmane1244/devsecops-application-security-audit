# 21 — Synthèse des risques et vérifications prioritaires

Date de consolidation : 29 octobre 2026. Cette synthèse s’appuie sur les 98 occurrences du scan initial, les fiches 01–20 et les lectures Docker en lecture seule. Elle hiérarchise les vérifications selon le chemin atteignable, le contrôle de l’entrée, l’impact potentiel et la solidité des preuves. Les sévérités Trivy restent consignées dans les rapports; elles ne déterminent pas seules la priorité opérationnelle.

## Comment lire les niveaux

- **Priorité 1** : vérifier d’abord un scénario dont un chemin applicatif vers un impact important est observé et dont un prérequis clé paraît plausible. Cela ne signifie ni vulnérabilité exploitable confirmée, ni incident.
- **Priorité 2** : impact potentiellement important, mais un réglage, une provenance de données, une condition de challenge, un flux de build ou une étape intermédiaire reste à établir.
- **Priorité 3** : le composant ou l’avis est détecté, mais le sink/prérequis n’est pas observé dans les consommateurs parcourus, ou la détection système appelle d’abord une validation de statut/version avant d’investir dans une analyse applicative.
- **Confiance** qualifie les preuves statiques de cette analyse, pas la probabilité d’exploitation. « Élevée » peut confirmer un appel sans confirmer que le service a reçu une entrée ou qu’il était actif.

## Alertes dont le sink n’est pas observé dans les chemins parcourus

Les fiches indiquent notamment que PBKDF2 ou une sortie `WordArray.random` sensible n’est pas utilisée dans les flux crypto-js inspectés; les fonctions lodash exactes de plusieurs avis ne sont pas exportées ou appelées par les consommateurs examinés; les appels Moment documentés n’analysent pas de chaîne hostile et ne transmettent pas de locale utilisateur; `uuid` n’est pas appelé avec `buffer`/`offset`; le consommateur `once` identifié ne fournit pas d’`AbortSignal`; la borne de version de l’avis MessageFormat exclut `2.3.0`. Ces constats abaissent la priorité des chemins examinés, sans prouver qu’aucun autre consommateur ou chargement n’existe. Voir [02](02-lodash.md), [04](04-crypto-js.md), [11](11-moment.md), [16](16-uuid.md), [17](17-messageformat.md) et [18](18-once.md).

## Vérifications restantes, dans l’ordre

1. **Confirmer la cohérence de l’artefact de déploiement et du chemin file-type** : éclaircir pourquoi le fichier compilé `build/lib/utils.js` de l’image s’arrête avant `asyncHandler`, vérifier la divergence avec `lib/utils.ts` publié, comparer le build attendu et l’image réellement déployée, puis établir si un service correspondant est en cours d’exécution. Le conteneur audité est arrêté; ne pas démarrer l’application dans le cadre de cette vérification.
2. **Finaliser les prérequis d’authentification JWT** : contrôler les options effectives par copie, la clé et la configuration de vérification sans divulguer les secrets, puis distinguer les avis dont le mécanisme est confirmé de ceux exigeant un fournisseur dynamique absent des appels trouvés.
3. **Établir les sources de configuration des chemins conditionnels** : challenges/safety mode, PAC/proxy, URL distantes de personnalisation, hôtes de téléchargement et options de templates. Les fichiers par défaut de l’image ne déterminent pas la configuration runtime passée ou future.
4. **Qualifier les entrées pouvant provoquer du coût ou une interprétation** : feedback passé à `sanitize-html`, headers de réponses dans la chaîne Got, paramètres MarsDB, expression notevil et contenu/chemin Handlebars. La priorité doit dépendre de l’authentification, des limites, des contrôles et du rôle de l’entrée, sans exécuter de payload.
5. **Examiner séparément le pipeline de build et les composants Debian** : inventorier les archives réellement acquises/extraites et achever le rapprochement des avis Debian, versions binaires et statuts de suite. Ce travail est distinct de l’exposition des routes de l’application.
6. **Étendre seulement si la preuve l’exige** la vérification des consommateurs hors périmètre dans les fiches marquées partielles. Une absence de sink dans les chemins observés reste une limite de recherche, pas une preuve universelle d’absence.

## État de l’évaluation

Les 98 occurrences restent inventoriées dans [20-bilan-scan-initial.md](20-bilan-scan-initial.md), mais elles ne représentent ni 98 scénarios indépendants ni 98 risques applicables. L’ID de configuration de l’image locale diffère de celui du rapport Trivy; les 24 DiffIDs concordent et la seule différence de configuration observée est le label `org.opencontainers.image.created`. Cette correspondance de couches rapproche les fichiers, sans transformer la lecture d’une image ou d’un conteneur arrêté en preuve d’état runtime. Aucun démarrage, scan, appel applicatif, test d’exploitation ou correctif n’a été réalisé. **L’audit reste ouvert; aucune exploitation n’est démontrée.**
