## Chaînes de dépendances et résolutions observées

- `decompress@4.2.1` est requis par `download@8.0.0` (`download/package.json`, dépendance `decompress: ^4.2.1`). L’import de `download` dans l’application (`lib/utils.ts:10`) résout cette copie de decompress via `node_modules/download/index.js:7`.
- `tar@6.2.1` est imbriqué sous `sqlite3@5.1.7`. `sqlite3`, son `node-gyp@8.4.1` imbriqué et `cacache@15.3.0` déclarent une dépendance tar compatible. Les imports observés par `sqlite3/deps/extract.js:1` et `sqlite3/node_modules/node-gyp/lib/install.js:5` résolvent tous deux `juice-shop/node_modules/sqlite3/node_modules/tar/index.js`.
- L’inspection des sources applicatives (TypeScript et build JavaScript) n’a trouvé aucun import direct de `decompress` ou de `tar`, ni aucun appel de ces API depuis une route. L’application ne reçoit donc pas, dans le périmètre inspecté, une archive utilisateur pour la transmettre à ces extracteurs.

## Parcours decompress : téléchargement au démarrage, sans extraction observée

**Preuve D-01 — appel applicatif.** `lib/utils.ts:110-118` définit `downloadToFile(url, dest, downloadData = download)`. La fonction appelle le téléchargeur avec `{ agent: proxyAgent }` (`:116`), puis écrit le Buffer reçu tel quel avec `fs.writeFileSync(dest, data)` (`:117`). Aucun paramètre `extract` n’est passé.

**Preuve D-02 — garde d’extraction.** `node_modules/download/index.js:80` n’appelle `decompress` que si `opts.extract` est vrai et que le contenu est détecté comme archive. Les branches d’écriture fichier (`:86-87`) ont la même condition. L’application fournit seulement l’agent réseau; l’option `extract` reste donc désactivée pour les appels observés. Le paquet decompress est chargé comme dépendance de download, mais son extracteur n’est pas atteint par ce chemin.

**Preuve D-03 — provenance et destinations.** Les appels à `downloadToFile` repérés sont des tâches de données/démarrage, pas des routes HTTP : valeurs `memory.image` vers un fichier image temporaire et images produit dans `data/datacreator.ts:343-346, 390`, un blueprint référencé par les données de produit (`:418`), fichiers personnalisés issus de la configuration dans `lib/startup/customizeApplication.ts:83-90`, et un overlay dans `lib/startup/customizeEasterEgg.ts:17`. Les fichiers sont enregistrés à la destination déterminée par ces tâches. Aucune archive ne leur est transmise avec extraction activée. La fonction n’applique pas de limite de taille applicative explicite au Buffer téléchargé; un éventuel plafond du client HTTP n’a pas été vérifié.

**Conclusion d’usage.** Les avis decompress décrivent des problèmes au moment d’extraire une archive. La version et le code concerné sont présents, et l’application déclenche des téléchargements au démarrage, mais le chemin observé écrit les octets sans extraction. Une archive éventuellement renvoyée par une URL de configuration serait donc enregistrée comme contenu brut dans ce chemin. Aucun flux de requête utilisateur vers `decompress()` n’a été observé. Cela limite l’applicabilité à ce chemin; cela ne prouve pas qu’aucun autre appel dynamique, outil de build ou consommateur hors périmètre ne puisse utiliser l’extracteur.

## Parcours tar : extraction pour la construction native

**Preuve T-01 — extraction SQLite au build.** `sqlite3/deps/extract.js:3-10` reçoit le chemin de l’archive en `process.argv[2]`, le répertoire cible en `process.argv[3]`, puis appelle `tar.extract({ sync: true, file: tarball, cwd: dirname })`. L’action de construction dans `sqlite3/deps/sqlite3.gyp:63` relie ce script aux sources SQLite; `sqlite3/binding.gyp` inclut ce fichier gyp. L’archive source SQLite présente dans le paquet est `node_modules/sqlite3/deps/sqlite-autoconf-3440200.tar.gz`; elle est fournie avec la dépendance, et l’extraction cible le répertoire de build transmis au script. L’appel n’ajoute ni filtre d’entrées ni limite globale explicite de taille.

**Preuve T-02 — en-têtes Node pour node-gyp.** `sqlite3/package.json` déclare un script d’installation qui tente un prébuild puis une compilation node-gyp. Dans `sqlite3/node_modules/node-gyp/lib/install.js:119-146, 150-168`, node-gyp peut extraire soit le tarball local choisi par `gyp.opts.tarball`, soit le tarball de version Node téléchargé depuis `release.tarballUrl`. La destination est `devDir` (`:50`), avec `strip: 1` et `filter: isValid`. Le filtre n’accepte que les extensions `.h` et `.gypi` (`:275-279`); il inspecte le nom de chemin, pas explicitement le type de l’entrée. Aucun plafond applicatif de données cumulées, de ratio ou de nombre total d’entrées n’est passé dans ces appels.

Ces appels sont dans le chemin de construction/installation de la dépendance native SQLite, pas dans le démarrage normal de Juice Shop ni dans une route. La présence du script install ne prouve pas quelle branche (`prebuild-install` ou compilation de source) a été exécutée lors de la construction de l’image. De même, la provenance exacte du tarball de node-gyp peut être l’URL de distribution Node ou une archive locale fournie par les options de build; cette configuration de build n’est pas établie par le rapport.

**Contrôles et limites observés.** node-gyp fixe un répertoire `cwd`, retire un niveau de chemin avec `strip: 1` et applique le filtre d’extensions. Le script SQLite utilise un `cwd` de build et une archive fournie avec le paquet, sans filtre personnalisé ni `strip` explicite. Aucun des appels ne désactive `preservePaths` ou n’ajoute une validation applicative explicite des cibles symlink/hardlink; ils s’appuient sur les contrôles internes de tar 6.2.1, version à laquelle plusieurs avis attribuent des contournements. Les deux chemins opèrent sur des archives de build (distribution Node ou dépendance SQLite), pas sur des archives envoyées par une route. Une compromission ou substitution de ces sources de build n’a pas été examinée.

## Conclusion provisoire

- **decompress** : la version 4.2.1 est signalée et chargée via `download`, mais son extraction n’est pas activée dans les appels applicatifs observés. Les quatre avis ne sont donc pas reliés à un flux d’extraction de requête utilisateur dans ce périmètre.
- **tar** : la version 6.2.1 est signalée et des appels `tar.extract` existent dans les scripts de construction de SQLite/node-gyp. Ils traitent des archives de build, pas des uploads ou des archives transmises à une route. Certains avis ont des prérequis absents dans les appels vus (API `replace`, liste de membres, OS macOS/Windows); les autres restent conditionnels à une archive de build malveillante ou substituée, ce qui n’a pas été observé.
- Les options repérées offrent des limites partielles (`cwd`, `strip`, filtre d’extensions node-gyp), mais aucune preuve ne permet de les considérer comme une protection générale contre les liens ou les tailles décompressées. L’analyse statique ne prouve pas qu’une archive d’installation a effectivement exploité ces chemins.

Les sources officielles des avis sont liées dans le tableau de rapprochement. L’inspection s’est limitée aux rapports fournis et aux fichiers applicatifs/de dépendances de l’image identifiée; les archives elles-mêmes, l’historique exact de l’installation et les configurations de build externes n’ont pas été examinés.
